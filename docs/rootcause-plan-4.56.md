# 4.56 根因方案：从「逐轮打补丁」到「可收敛的生成系统」

> 触发：用户反馈「生成过程中一直出现章节生成异常」「还是在打补丁的修复，并没有实际解决」。
> 本文先量化现象、再归因到架构层，最后给出改造方案与分期路线。
> 全部数据来自真实生成（项目 `3c3f04667c69`，巢湖模板）的落盘 draft，可复现。

---

## 一、现象量化：用户看到的「异常」到底是什么

### 1.1 每个 draft 的非成功阶段统计（最近 12 次真实生成）

| 阶段 | 出现次数 | 说明 |
|---|---|---|
| `agent-requirement-response-repair` **failed** | **20** | 招标要求响应补写（每 draft 1~2 次） |
| `agent-length-compression` **failed** | **15** | 篇幅压缩（每 draft 1~3 次，常"已回滚"） |
| `global-consistency-repair` failed | 11 | 跨章一致性修复残留 |
| `agent-content-depth-repair` failed | 11（+ partial 7） | 内容深度补写残留 |
| `templating-repair` failed | 10 | 模板化残留 |
| `authority-audit` failed | 10 | 无主数值缺口 |
| **`chapter_generation` failed** | **7** | **章节生成失败**（用户直接看到的"章节生成异常"） |
| `agent-numeric-verification` partial | 7 | 数值核对未清零 |
| `citation-adjudication` / `requirement-tail-closure` failed | 5 / 5 | 引用裁决、要求链尾收口 |

**关键事实：每一次生成，用户都会看到 5~10 个红色/黄色阶段。** 这不是偶发——是**常态**。

### 1.2 章节生成失败的两种形态

| 形态 | 实例 | 后果 |
|---|---|---|
| **块失守 → 整章阻断** | `doc-f00280f9`：第 1 章 34 块中 1 块密度失守 → **整章丢弃** → 文档 33,570 字（目标 50,000）、BOQ 落位 52.8% | 篇幅腰斩、评分从 85 掉到 83 |
| **任务中断** | `doc-40fc19b3`/`doc-cd4c5178`：`生成任务已中断，请点击继续生成或重新生成` | 需人工干预 |

### 1.3 修复轮的「成功标准 = 零残留」制造了红灯墙

修复轮的语义是「把该类缺陷清零」，于是：
- 残留 1 条 → `failed` / `partial`；
- 用户看到的是「修复失败」，而实际是**部分收敛**（如残留轨迹 105→54→42）。

4.55.27 已引入三档 `success/partial/failed`，但**成功率本身仍然低**——因为轮次预算与收敛保证不足。

## 二·零、**上游根因 R0：写作侧系统性欠产，修复链替它还债**

> **用户判断成立**：内容不是"写作写出 100%、修复链多加了 66%"，而是
> **"写作只写出 65~87%，修复链从缺口补起、补到超过预算 66%"**。
> 修的是写作侧的账，但还债的人没有预算观念。

### R0.1 实测：写作完成率 65~87%，且系统自己报出来了

`doc-1790144107028-aaba7ba3` 的 `chapter_generation` 阶段 details 逐字：

| 章 | 章预算 | 写作完成 | **本轮完成率** | 二级小节 |
|---|---|---|---|---|
| 第一章 | 30,600 | 26,674 | **87%** | 30 |
| 第二章 | 11,856 | 7,652 | **65%** | 6 |
| 第三章 | 7,544 | 5,168 | **69%** | 4 |
| 合计 | 50,000 | 39,494 | **79%** | — |

**"完成率"被计算、被写进阶段详情，却没有任何机制要求它达标**——它只是一个观测值。

### R0.2 代码层：欠产被"合法化"，且与超产处理**严重不对称**

`chapterGeneration.ts` 的块级篇幅合同（注释与代码逐字）：

```
达标区 [0.85,1.15]：直通
欠产侧 [0.7,0.85)：**记录放行**（注释理由：「规划层已把块预算校准到模型自然输出区间，
                    微缺口重写收敛期望为负」）
       <0.7：仅首轮（attempt 0）阻断补足重写一次，**二轮仍欠产放行**
超产侧 >1.15：前轮一律阻断重写；末轮放宽到 1.2× 接受
             ；仍 >1.2× 判块失败 → 隔离重写 → C7 章级对冲接纳
```

三处不对称：

| 维度 | 欠产侧 | 超产侧 |
|---|---|---|
| 门线 | **0.7×** | 1.15×（末轮 1.2×） |
| 末轮 | **完全不设门**（`attempt === 0 && …`） | 保留 1.2× 门 |
| 处置 | 记录放行 | 阻断重写 + 隔离重写 + 章级接纳 |

注释自己写着「4.40 双向硬合同 = [0.85,1.15]」——但欠产侧的实际门线是 **0.7**，
而**反馈**给模型的下限是 `charFloor = 0.85×`。
**即：要求写手写 0.85，实际只验收 0.7。** 结果是模型稳定输出在 0.8× 附近
（代码注释自述「产出落到 0.81~1.25x 块目标」），章完成率就稳定停在 79%。

### R0.3 债务转移：欠产 → 检测报缺 → 修复链无预算补写 → 超产

```
块欠产（[0.7,0.85) 记录放行、末轮无门）
   ↓  章完成率 65~87%
章内容不足 → 被"内容深度 / 事实密度 / 清单落位 / 要求响应"等检测器识别为缺陷
   ↓
修复链补写：**无章级预算、无文档级预算、不知道别的轮已经写了什么**
   （contentDepthRepair / requirementResponseRepair / controlLoopRepair /
     professionalChainRepair / requirement-tail-closure（一次插 54 条）…）
   ↓  +26,058 字（+66%），且**不是重复内容**（完全重复段落 0，近重复句 7/799）
终稿 65,552 字（预算 50,000，+31%）→ 篇幅超限
   ↓
lengthCompressionRepair 想压回来 → 信息守恒守卫（字数须降 + 标题/数值零缺失 + 表格行数不减）
                                面对万字级真实内容压缩必然回滚 → 每轮回滚
```

**闭环结论**：欠产被放行 → 债转给修复链 → 修复链无预算 → 补成超产 → 压缩轮压不回来。
**整条链的起点是 R0。**

### R0.4 后果不止篇幅

- 修复链补写的内容**质量参差**：补写轮只对"某一类缺陷"负责，缺少写作期的整体结构设计 →
  这正是**空小节、规划小节未落位、跨条目串值、表执行率波动**的来源。
- 用户看到的"短句/残句"也与此相关：补写/清洗轮反复追加与裁剪，句子被切碎的概率上升
  （而对应的 `truncated-sentence` 检测器恰恰没接线，见 R3）。

### R0.5 修复方案（**优先级最高，前置于改造 1~5**）

| # | 改动 | 说明 |
|---|---|---|
| **R0-a** | **欠产侧与超产侧对称化**：欠产门线 0.7 → **0.85**（与下发反馈口径一致），**末轮同样保留** | 一行常量 + 一处条件。风险：欠产块变多 → 必须配 R0-b，不能只加门 |
| **R0-b** | **欠产块"续写"而非"判死"**：欠产块不整块重写，而是带「还缺 N 字 + 该块要点清单」做**增量续写**（保留已写内容，追加展开）；续写仍有界（≤2 轮） | 这是与 4.55.30「块失守不丢弃」同族的下半句：**不丢弃 → 而是补齐** |
| **R0-c** | **章级完成率进门禁**：`本轮完成率 < 0.85` 时**在写作期就地补齐**（按小节缺口分配续写），而不是留给修复链 | 该数值已在算，只是没被用 |
| **R0-d** | **写作期/修复期职责切分**：写作期负责**篇幅**（R0-a~c），修复期只负责**缺陷**（事实/一致性/格式）；修复链的任何写入受改造 2-b 的**预算账**约束（超额必须替换而非追加） | 与改造 2 强耦合 |
| **R0-e** | **`maxTokens` 复核**：`max(3200, targetWords×1.5)` 假设「思考 token 与正文共享输出池」，对 target≈1,900 的块可能不足。需按「思考预算 + 正文预算」分离估算，或按实测校准下限 | 见下方「欠产机制的判别实验」 |

#### 欠产机制的判别实验（已排除一个假设，剩一个待验）

**已排除：材料不足。** `doc-aaba7ba3` 的 `agentWorkflow.chapterTasks` 显示每章证据充足：

| 章 | 证据条数 | 证据字数 |
|---|---|---|
| 主要施工方法与技术措施 | 1,891 | 1,078,005 |
| 确保工期与质量… | 2,105 | 1,070,670 |
| 工程重难点及危大工程… | 2,166 | 1,099,237 |

**剩余假设：单次调用输出上限（R0-e）。** 完成率与块目标大小呈**明确的反向关系**：

| 章 | 块数 | 块目标（章预算/块数） | **完成率** |
|---|---|---|---|
| 第一章 | 34 | ≈900 | **87%** |
| 第二章 | 6 | ≈1,976 | **65%** |
| 第三章 | 4 | ≈1,886 | **69%** |

块目标越大 → 完成率越低，符合"每次调用的输出量被某个上限截住"的形态（与材料多少无关）。

**判别实验（1 次生成、约 10 分钟）**：取第二/三章各 1 个块，把 `maxTokens` 从 `max(3200, target×1.5)`
临时翻倍，其余不变，对比输出字数：
- 输出显著上升 → **确证 R0-e**（修 maxTokens 预算模型）；
- 输出不变 → 排除 R0-e，转向"提示词/风格门禁抑制展开"（该章主题多为制度性表述，
  而模型同时被禁止写套话——预算要求写满 vs 质量门禁禁套话的张力）。

**验收**：
- 章完成率（写作期）≥ 95%；
- 终稿字数 ∈ [0.95, 1.15] × 预算（当前 1.31×）；
- **修复链的净增字数 ≤ 5% 预算**（当前 +66%）——这是"写作侧真的修好了"的硬指标。

## 二、根因（架构层，5 条）

> 判据：**能解释"为什么每轮都在修、每轮都还在"** 的，才算根因。

### R1 写作侧把「质量目标」实现成「硬合同 + 丢弃」——失败是零和损失

- 块级写作有 **7 类硬合同**（篇幅区间、结构契约、事实密度、模板化、归因量化、数值、格式），
  **任一不过 → 块判死 → 隔离重写 1 次 → 仍不过 → 章阻断或降级**。
- 丢弃的是**已经生成好的内容**：`doc-f00280f9` 里 33/34 块成稿却整章丢弃。
- 架构问题：把"内容质量"当成**判定**而不是**目标**。没有"打分 → 定位最弱项 → 定向改进"的循环，
  只有"过线 or 死"。LLM 生成是**概率过程**，硬合同必然产生固定比例的失败。

### R2 修复链是「无预算的追加」，且靠「链尾重放」互相打补丁

- **实测**（`doc-aaba7ba3`）：写作完成时三章 26,674/7,652/5,168 = **39,494 字，全部低于章预算**；
  终稿 41,878/14,013/9,661 = **65,552 字**，各章 **+57% / +83% / +87%**。
  → **超产 100% 发生在写作之后的修复链**（+26,058 字）。
- 且**不是重复内容**：正文 40 个长段落中完全重复 = **0**，799 句中前 24 字重复仅 **7 句**。
  → 事后的"压缩"路线注定低效。
- 修复轮各自只解决"自己那一类缺陷"，**不知道章预算、不知道别的轮已经写了什么**：
  `contentDepthRepair` / `requirementResponseRepair` / `controlLoopRepair` / `professionalChainRepair` /
  `requirement-tail-closure`（一次插 54 条）都只做追加。
- 为了对抗"后面的轮重建 markdown 把前面的修改冲掉"，链尾堆了 **6+ 个 `replayXxx`**：
  `runSurfaceDeterministicCleans` / `replayBlueprintCitationNumericFixes` / `replayStage5FactsModelNumericFixes` /
  `replayRequirementTailClosure` / `replayTailStrippedBasisCitations` / `replaySurfacePunctuationClosure`…
  这是**用更多补丁维持补丁**——正是用户说的"在打补丁"。

### R3 缺陷判定散落在 ~50 个文件，一致性靠注释维持——登记与接线会漂移

- **实测**：6 个检测器（`truncated-sentence` / `atlas-reference-phrase` / `source-enumeration` /
  `meta-discourse-declaration` / `finish-thickness` / `formula-residue`）**已登记、`det()` 调用点全为 0**。
  写作侧无约束、检测侧无报告、修复链无消费——**三处同时失明**，用户看到的残句/指向型就是这样漏出去的。
- 同类问题：单位别名表 ≥4 份副本、豁免正则多处各写一份、`authorityAudit` 模块头承诺的
  "链尾 demote 收敛器"**早已是停用桩**（承诺与实现脱节）。
- 架构问题：**没有可执行的一致性契约**。"单源声明"只写在注释里，没有测试能拦住漂移。

### R4 变更语义（答疑/澄清）没有一等公民通道

- 答疑文件确已入库并被检索（补疑文件路径在证据池出现 1,483 次），但**技术性修正**（改为/取消/不涉及/需要）
  约一半没进正文（实测：混凝土满包 / 304 不锈钢防滑条 / 绝对标高 8.00 / 以围墙为一二期分界 全为 0 次）。
- 现有唯一的"答疑生效层"只认**带口径标签的单值**（合同金额/计划工期/开工日期/暂列金额）。
- 架构问题：把"资料"当成**一堆可检索的证据**，而不是**带时序与变更语义的账本**。

### R5 评分口径把「门禁断言」与「质量度量」混在一个数里，形成峭壁

- `事实完整与一致性 = 0.6×max(0, 100−冲突数×20) + 0.2×绑定 + 0.2×关键事实`——**≥5 条冲突即归零**。
- 多个子分是 0/100 二值（强制模块覆盖率、题注覆盖率、参数义务 90% 门槛）。
- 八轮实测该维度 0~40 分，是唯一稳定拖分的维度；90 分的瓶颈恒在此。
- 架构问题：**"能不能交付"（布尔）**与**"质量多少分"（连续）**应当分离；当前把门禁阈值塞进评分公式，
  导致"3 条真实缺陷"与"30 条"在分数上等价。

## 三、架构改造方案（4.56）

> 总纲：**先把写作侧写到应写（R0），再把"生成 → 检测 → 补丁"的流水线改成"生成 → 度量 → 有界改进 → 收敛判定"的闭环**，
> 并为闭环建立三本账：**预算账、变更账、契约账**。

### 改造 1（对应 R1）：块级写作从「硬合同」改为「下限合同 + 评分 + 定向改进」

| 项 | 现状 | 改造后 |
|---|---|---|
| 块失败判定 | 7 类硬合同，任一不过即判死 | 保留**下限合同**（安全/事实/格式红线，不可降），把**质量类目标**（密度、归因、结构丰富度）改为**打分** |
| 失败处置 | 丢弃块 → 章阻断/降级 | 保留内容 + **显式标注该块的弱项** + 进改进队列（有界轮次） |
| 章级失败 | 整章丢弃 | **不丢弃**：章以"通过下限的块"成稿，弱项进改进队列；仅当"下限合同"失守（安全/事实/格式）才阻断该块 |
| 改进循环 | 无（只有"重写一次"） | 按**弱项排序**做有界定向改进（每章 ≤N 轮，每轮只改最弱的 K 块） |

**为什么这不是"降标"**：丢弃已经正确生成的内容本身就是缺陷（33/34 块成稿却整章不要）。
真正要守住的是**下限**（事实/安全/格式红线），质量目标应当**可度量、可改进**，而不是"过线或死"。

**验收**：`chapter_generation` failed 率 → 0（下限合同失守除外，且逐条列明）；
`doc-f00280f9` 同形态输入复算 → 章不丢、篇幅回到预算区间。

### 改造 2（对应 R2）：建立「文档状态 + 预算账本」，收敛所有重放

| # | 改动 | 说明 |
|---|---|---|
| 2-a | **单一写入通道**：所有对正文的写入（写作/补写/清洗/替换）必须经 `applyDocumentEdit(scope, edit)`，由它统一维护 ①章字数 ②预算余量 ③变更日志 ④provenance | 现状是每个轮直接改 `session.finalMarkdown` 或 `chapter.content` |
| 2-b | **预算账在写入时强制**：每次写入前检查「本 scope（章/文档）剩余额度」；超额即**拒绝追加**并要求"替换/合并"（把 4.55.36 的 4-3-a 从"建议"变成"机制"） | 现状：无预算概念，追加无上限 |
| 2-c | **重放管线合一**：把 6+ 个 `replayXxx` 收敛为**一条有序重放链**，每步声明"输入条件 / 幂等性 / 与哪些步互斥"；由统一调度器按序执行与验证 | 现状：散落各处的重放靠注释说明先后 |
| 2-d | **删除"重建即回退"这一根因**：`rebuildFinalMarkdown` 从章 drafts 重拼会冲掉 markdown-only 修改——改为**单一真相源**（要么只写 drafts，要么只写 markdown，不同时维护两份） | 这是 6 个重放存在的**唯一原因** |

**验收**：重放调用点数从 6+ 降到 1；终稿字数与"写作完成字数 + 各轮批准的增额"逐笔对账一致（±3%）；
`doc-aaba7ba3` 同形态复算 → 终稿 ≤ 预算 ×1.15。

### 改造 3（对应 R3）：可执行的一致性契约（契约账）

| # | 改动 | 说明 |
|---|---|---|
| 3-a | **登记即接线**：注册表校验扩展到「登记的检测器必须有 `det()` 调用点」；反之亦然。测试红即阻断 | 直接消灭 6 个哑火检测器这类问题，并防复发 |
| 3-b | **判据单源化清单**：单位别名、豁免正则、阈值表、口径集——每类注明**唯一来源文件**，并写"反重复校验"测试（同名常量/同形正则出现在第二处即红） | 现状：单位别名 4 份副本、豁免多处各写 |
| 3-c | **承诺可执行**：模块头/注释里承诺的机制（如"链尾 demote 收敛器"）必须有对应实现与测试，否则从注释删除 | 现状：承诺与实现脱节 |
| 3-d | **每个检测器三选一**：①有确定性修复路径 ②有 LLM 修复轮消费 ③显式标 `manual_review` 并进人工清单。不允许"报了没人管" | 现状：25 个 blocker 级孤儿（无修复路径） |

**验收**：一致性契约测试全绿；"检测器 → 修复路径"映射表 100% 覆盖（无孤儿）。

### 改造 4（对应 R4）：变更账本（答疑/澄清 = 一等公民）

| # | 改动 | 说明 |
|---|---|---|
| 4-a | **统一变更账本**：把值级口径（`valueOverride`）与技术性修正（新增 `clarificationAmendments`）合并为一条账本，条目统一为 `{ subject, attribute, before?, after, action, source, order }` | 单一真相，避免两套口径打架 |

### 改造 5（对应 R5）：门禁与度量分离

| # | 改动 | 说明 |
|---|---|---|
| 5-a | **门禁布尔化**：`buildExportGate` 只回答"可否交付"，输出**阻断清单**（每条带检测器、位置、修复路径 or 人工） | 现状：门禁与评分共用一套 issue 计数 |

**验收**：给出「当前配置下 95 分的可达性证明 or 不可达结论」。
