4.55.17 答疑澄清生效层（招标写 365、答疑澄清为 330 时，全文必须只用 330）

**现象**（用户反馈 + 终稿实测）：巢湖项目招标文件工期 365 日历天、答疑「现变更修改为 330 日历天」，
基本信息表用了 330（对的），但**正文与进度计划仍按 365**——终稿里三种表述并存：
「本工程总工期为365日历天」／「变更修改为330日历天」／「按330日历天总工期倒排」，
进度替代表起止天序排到**第 348 天**（按 365 编排）。开工日期同样双值（招标 2026-08-31 / 答疑 2026-10-10）。

**根因**（三层各取各的口径）：
1. 蓝图 `extractContractFromFacts` 取文本**首个**工期匹配（365）→ 里程碑/劳动力/进度计划全按 365 推导；
2. 事实层虽有来源优先级（addendum 96 > 招标），但答疑抽出的值常是**残片/指向形态**——
   canonical 里两条工期值：「见招标公告计划开工日期：2026年08月31日…」（标为 addendum 却携带招标旧值）
   与「现澄清为如下：条款号…计划开工日期：2026年10月10日…」（真答疑值埋在残片里）；
3. 同字段两个 key（duration / schedule_requirement）未归并，两值并存进入正文。

**处置**：
- 新增 `clarificationOverrides.ts`（答疑澄清生效层，零 LLM）：抽「生效值 + 被取代值 + 来源」override 表。
  判据：变更句式（「365日历天，现变更修改为:330日历天」/「由365调整为330」）优先；
  答疑来源平铺陈述的值生效、招标来源的值登记为被取代；**「见招标公告…」按句识别为招标口径指针**
  （巢湖实锤：答疑文件里引用的仍是招标旧值，不得当答疑值）。
- 蓝图层：`resolveEffectiveTotalDays`（变更后口径优先）替换首个匹配解析；
- 写作层：`renderClarificationConstraintBlock` 渲染为全文硬约束注入写作简报
  （「现行为 X；已被取代不得再作为现行口径：Y」）；
- 终检层：`superseded-value-usage` 检测器——旧值以现行口径出现即 blocker（引用变更过程形态豁免），
  与写作约束同源，约束未被遵循时暴露。

**回归**：全仓 339 文件 / 14,464 用例通过（新增 7 项：变更句式两形态 / 指针识别实锤 / 无变更静默 /
约束块渲染 / 来源判定 + 4 项进度超声明工期）；typecheck 与 eslint 全绿。
